# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is
Wikitizer turns a D&D group's exported text-chat logs into structured worldbuilding lore (a free WorldAnvil alternative). The pipeline is: raw chat logs → pure-Python parser → LLM agents that extract structured lore → wiki output.

## Commands
- Activate env: `source venv/bin/activate`
- Run all tests: `pytest` (run from repo root) — the fast, mocked suite; now **excludes** anything marked `integration` (via `addopts = -m "not integration"` in `pytest.ini`).
- Run the live extractor tests: `pytest -m integration` (makes real Anthropic API calls; needs `ANTHROPIC_API_KEY`). Opt-in only.
- Run one file: `pytest tests/test_speaker_map.py`
- Run one test: `pytest tests/test_speaker_map.py::test_load_speaker_map`
- Build the speaker map from real logs (interactive, one-off): `python scripts/build_speaker_map.py`

## Hard constraints
- **Python 3.9.6.** `dict[str, str]` / `list[X]` builtin generics are fine (PEP 585), but `X | None` union syntax is NOT supported — use `Optional[X]` from `typing`. A 3.10 upgrade is deferred.
- **`logs/` is gitignored and must never be committed.** Files there contain real phone numbers. Keep all chat data local.
- Always pass `encoding="utf-8"` when reading/writing files (names may contain accented chars).
- **The Anthropic API key lives in `.env` (gitignored) as `ANTHROPIC_API_KEY`** and is loaded into the environment by `main.py`'s `load_dotenv()`; the SDK reads it from there. Never read or hardcode the key in source — `agents/base.py` deliberately doesn't (it leaves key-loading to the SDK/entry point). Note the SDK (v0.104) does NOT validate the key at construction; a missing key only surfaces at request time.

## Architecture
Phased build; most of it is still ahead. Current + planned structure:
- `models/` — pydantic v2 data models. `message.py` (`Message`) is parser output; `lore.py` (`Quote`, `Location`, `Character`, `HistoryEvent`, `Organization`, `Item`, `PeopleAndCultures`, plus the `Scope` `(str, Enum)` for `HistoryEvent.scope`) is the LLM-extraction schema. Use `Field(default_factory=list)` for list fields so instances don't share state. `Scope` is `world`/`regional`/`personal`; the `(str, Enum)` mix-in (3.9's stand-in for 3.11's `StrEnum`) makes `Scope.WORLD == "world"` true so it JSON-serializes cleanly and renderer `== "world"` checks keep working, while the Enum makes pydantic **reject** any off-menu value. All six entity models — `Location`/`Character`/`HistoryEvent`/`Organization`/`Item`/`PeopleAndCultures` — carry a `name` + `aliases` so the Phase 4.1 reconciler can match them all the same way. The three typed categories `Organization`/`Item`/`PeopleAndCultures` are **exact `Location` clones** (same four fields) that replaced the retired `OtherDetail` catch-all; the per-category inclusion discipline lives in each one's extractor prompt (separate later phases), not in the schema, and the "tie" of a nameless Org/Item (e.g. "an agency in Crown's Nest", "CJ's amulet") stays in the prose `details` for the cross-link pass, never a `tied_to` field. `reconcile.py` (done, Phase 4.1a) holds the **decision-object contract** the reconciler LLM hands back — `ReconcileDecision` (`merges` + `possible_duplicates`, both `default_factory=list`), `MergeGroup` (`members` = 0-based **indices** into the input list, a `canonical` heading, and a usually-empty `conflicts`), `PossibleDuplicate` (a suspicious-but-unmerged pair + `note`), and `DetailConflict` (carries each side's **detail text + source**, NOT a `detail #N` coordinate, because the stored detail/quote lists keep no clean index-to-index mapping). One model set covers all six entity types — a decision is just indices + names, never a type-specific field — and anything not named in `merges` is an **implicit singleton** (the LLM never echoes unique entries, so the common case is cheap and a forgotten entry just stays its own page, the harmless under-merge direction).
- `speaker_map.py` (top-level) — `load_speaker_map(path) -> dict[str, str]`. Loads `config/speaker_map.json`, a flat map of phone number → name. Phone keys start with `+`; the special `"exporter"` key names whoever exported the chat (their messages have a bare timestamp, no phone prefix). Loader is deliberately minimal — lets `FileNotFoundError`/`JSONDecodeError` bubble up.
- `config/` — data only, no source. Holds `speaker_map.json`.
- `scripts/build_speaker_map.py` — one-off helper (discover phone numbers via regex → prompt for names → save JSON). NOT part of the runtime pipeline. Edit the `files` list inside to point at the real logs.
- `parsers/` — pure Python, no LLM; separate single-responsibility functions. `chat_parser.py` (done, Phase 2.1) turns a log into `list[Message]` via `parse_chat_log(filepath, speaker_map)`: a state machine over two **footer** regexes (the `+phone`/bare-timestamp line *ends* a message and names the sender of the block *above* it — a footer, not a header). `read_clean` reads raw bytes and strips `\r` to dodge the `\r\r\n` double-blank-line trap. Group files attribute the sender by footer phone; the 1-on-1 file has no phones, so it attributes by body left/right alignment. `reaction_filter.py` (done, Phase 2.2) strips export-artifact noise via `filter_reactions(messages) -> list[Message]`: a **pure** function (returns a new list; never mutates the input or its `Message`s — clones changed ones with pydantic v2 `model_copy`) that does NOT parse and does NOT call an LLM. Because `chat_parser` has already merged every multi-line message — including wrapped reactions whose closing quote was stranded on its own line (Pattern 7) — into one `.content`, it checks each content as a **single string** and keys off a fixed opener vocabulary at the *start*, rather than scanning line by line. It drops reaction/tapback pseudo-messages in both English **and** Spanish, across quoted (`Loved “…`), image (`Loved an image`), and emoji (`Reacted 😀 to “…`) forms — matched with **curly** quotes (U+201C), since a straight `"` matches zero reactions (Pattern 10). The opener set was verified exhaustive against all three real logs. Bare `[photo]` tokens are stripped but their captions are kept (captions can be real lore, Pattern 8). URL / link-only filtering is intentionally NOT here — a bare link is human-typed content, not an export artifact, so judging it is deferred to the Phase 3 LLM noise filter.
- `agents/` — LLM layer. `base.py` (done, Phase 3.1) is the shared foundation every specialized agent inherits. `BaseAgent.call_claude(system_prompt, user_message) -> str` makes one Messages API call (defaults: model `claude-sonnet-4-6`, `temperature=0.2`, `max_tokens=4096`) and concatenates the `.text` of every text-type block in the response. `call_claude_json(...)` runs that through `strip_code_fences` then `json.loads`, re-asking up to `max_json_retries` times (default 3) on a `JSONDecodeError` before raising `ClaudeJSONError` (which carries the last raw text); it logs a warning per parse-retry. **Two retry layers, on purpose:** transient HTTP failures are handled by the SDK's own `max_retries=3` (set when `BaseAgent` builds the real `anthropic.Anthropic`), so `call_claude` has NO manual loop; the JSON-parse retry is separate because a 200-response-with-bad-JSON is a different failure the SDK won't retry. The `anthropic` client is **injectable** (`client=`) so tests pass a fake and never hit the network or need a key. `strip_code_fences(text)` is a pure, dependency-free helper that strips a wrapping markdown code fence — a leading three-backtick line (optionally followed by `json`) and the matching trailing three-backtick line — returning text unchanged when there's no clean wrapper (Claude sometimes fences JSON even when told not to). Optional dev cache: **off by default** (constructor `cache=` or env `WIKITIZER_LLM_CACHE`), keyed on a sha256 of `(model, system, user)`, written to gitignored `.llm_cache/`. It lives in `call_claude_json` and caches **only responses that already parsed** — caching pre-validation text would let a cached bad response replay on every retry and defeat the JSON re-ask on re-runs; `call_claude` is intentionally cache-free. `noise_filter.py` (done, Phase 3.2) is the first specialized agent and the only **classifier** (the rest are extractors): `NoiseFilterAgent(BaseAgent).classify(messages) -> list[tuple[Message, str]]` labels every surviving message `lore` / `mechanic` / `noise` / `ambiguous`, paired with its original `Message` in input order — a cheap, high-volume funnel so the expensive extractors only ever see worldbuilding. It classifies only (no extracting/summarizing/rewriting/quoting), which is what lets it run on **Haiku at `temperature=0`** — both overridden via `setdefault` so `client=` injection still works, while `batch_size` (default 50) is a named param kept out of `**kwargs` so it isn't forwarded to `BaseAgent`. It chunks into batches and sends each as a JSON array of **batch-local 0-based integer IDs** (`{"id", "content"}`, `ensure_ascii=False`), asks Claude for `{"id", "label"}` back, and does the rejoin in Python — so Claude refers to messages by number and never echoes their text, and a stray id can't drift across batches. **`ambiguous` is the universal safe fallback:** every failure path — a `ClaudeJSONError` (logged at error, whole batch ambiguous), a non-list response, an unknown/extra id, a junk label, a missing id, or a non-integer id — resolves to `ambiguous`, never `noise`, because a wrongly-dropped `noise` loses lore forever while an `ambiguous` still flows downstream (and surfaces in the Phase 5 review log). One non-obvious validation trap baked into a test: a JSON float (`1.0`) or bool (`false`) id compares equal to and hashes like an int, so it would slip an `in range(n)` check **and** collide with a real id in the `{id: label}` dict — the guard uses `type(...) is int` (not `isinstance`, which would admit `bool`). `select_for_extraction(classified) -> list[Message]` is a pure helper encoding the default-include policy (keep `lore` + `ambiguous`, drop the rest) in one testable place. `classify` is deliberately **sequential**; fanning batches out over threads is the Phase 4 orchestrator's job. `base_extractor.py` (done, Phase 3.3 Step 2) is `BaseExtractor(BaseAgent)`, a **second** shared layer the *extractors* (not the classifier) inherit — so the inheritance is `LocationsExtractor(BaseExtractor)`/`BaseExtractor(BaseAgent)`, NOT extractors off `BaseAgent` directly. It owns the **template-method** spine — `extract(messages) -> list` (empty → `[]`, zero calls; else chunk by `batch_size` and concat `_extract_batch`), `_extract_batch` (build the batch-local `{"id","content"}` payload with `ensure_ascii=False`, call Claude, validate the array, dispatch each entry to `_build_entry`), and `_resolve_quote` — leaving subclasses just a `system_prompt` (class attr) + a `_build_entry(raw, batch)` that shapes one response object into one model; the base's `_build_entry` is a `NotImplementedError` stub. Unlike the noise filter it does **not** override model/temperature — extraction wants careful reasoning, so it keeps `BaseAgent`'s **Sonnet @ `temperature=0.2`** and changes only output size via `kwargs.setdefault("max_tokens", 8192)` (an extractor reply — full entries + verbatim quotes — is far fatter than `{"id","label"}` rows, and a reply cut off mid-JSON fails to parse, retries, gets cut at the same spot, and dies as `ClaudeJSONError`). `batch_size` (default **20, PROVISIONAL** — real value is a later design fork) and `verify_quotes` (default `True`) are named params kept out of `**kwargs`. **Claude never supplies metadata:** each detail cites a message by batch-local `source_id`, and `_resolve_quote` looks the `Message` up to attach `speaker`/`source_file` itself — so a wrong speaker is structurally impossible. `_resolve_quote` guards the id with `type(source_id) is int` (the same float/bool trap the noise filter documents — `isinstance(True, int)` is `True`, so a bool id would index `batch[0/1]` and silently attach the wrong message), bounds-checks it, then runs the verbatim check. **Verbatim-quote verification** (the anti-hallucination core): two pure module-level helpers, `_normalize_for_match` (fold curly quotes/apostrophes U+2018/2019/201C/201D → straight, squeeze all whitespace to single spaces, strip — but **not** lowercased, since case is a real change) and `_quote_is_verbatim` (normalized-quote substring of normalized-message). It absorbs the two near-guaranteed cosmetic mismatches (Claude flattens a multi-line message's newlines; Claude may retype curly punctuation straight) without admitting a genuine reword. One trap baked into a test: an empty/whitespace-only quote normalizes to `""`, a substring of everything, so it's treated as **NOT** verbatim — else a fabricated detail with a blank quote would sail past the guard. The normalizer is deliberately **minimal** (whitespace + curly only); em-dash/ellipsis folding is added only from a real false-alarm in the Phase 5 review log, never speculatively. A failed verbatim check **drops that detail and logs loudly** (the failure you can see beats the one you can't — with `verify_quotes=False` an unverified quote reaches the wiki silently). Error philosophy mirrors the noise filter, minus the universal `ambiguous` bucket: never crash, contain failures, log at three levels — a bad **batch** → `[]` + `error`, a bad **entry** → skipped + `warning`, a bad **detail** → dropped + `warning`. `noise_filter.py` and the extractors share nothing but `BaseAgent`'s plumbing; **no entity/alias merging** happens here even within a batch (a location returned twice is emitted twice — reconciling is Phase 4.1), and identical quotes are deduped within a single entry while its `details` are kept 1:1. `locations_extractor.py` (done, Phase 3.3 Step 1) is `LocationsExtractor(BaseExtractor)`, the first extractor: `extract(messages) -> list[Location]`, supplying only the locations `SYSTEM_PROMPT` and a `_build_entry` that pulls `name` (skip if not a non-empty str), defensive `aliases` (string-only, and only if a list), and detail/quote/`source_id` triples into a validated `Location` (catching `ValidationError`). `characters_extractor.py` (done, Phase 3.4) is `CharactersExtractor(BaseExtractor)`, the second extractor: `extract(messages) -> list[Character]` (inherited unchanged), supplying a roster-aware system prompt and a `_build_entry` whose detail/quote loop mirrors the locations one and adds three character-specific fields. Its whole reason for existing beyond "locations with more fields" is the **player/character conflation trap**: the chat mixes the real human "Sam, you free Thursday?" with the character "Sam plays Kriggy", and we must not mint a character named after a real person out of table talk. Two layers guard it, **neither baking real names into committed source** (the repo is public): (1) the **roster threads in at runtime** — `__init__` takes a **required** `player_names` (the real names, which the orchestrator sources from the speaker map's *values*; the extractor itself does no file I/O) and fills a literal `__PLAYER_ROSTER__` placeholder in the prompt via **`.replace()`, NOT `.format()`/f-string** (the prompt is full of literal `{ }` in its JSON example and `.format()` would treat each brace as a fill-in slot), `sorted()` for a byte-stable prompt so caching can kick in later; `system_prompt` is set as an **instance attribute** (quietly takes precedence over the class attr `LocationsExtractor` uses — zero `BaseExtractor` changes), and a lowercased `_roster_lookup` set powers the checks (blank/whitespace names are filtered out first, so an effectively-empty roster *disables* the check instead of building a truthy `{""}` that would null every `player_name`). (2) A **Python-side roster check**: `is_pc` (non-bool → `False`, the NPC default), `player_name` (`Optional`, validated against the roster **case-insensitively** and nulled-with-a-warning if it isn't a known real person — but an **empty roster disables the check**, and it **validates without rewriting**, so a matched `"sam"` stays `"sam"`), and a **name-collision flag** (a character whose `name` matches a real person is **KEPT but logged**, never dropped — a coincidence/in-joke is legitimate, and this log is the safety net that makes the softened prompt safe, catching the one mix-up the `player_name` check can't: a real-name character *with* that same `player_name`). The model change this phase: `Character` gained an `aliases` field mirroring `Location`'s **exactly** (same name, `Field(default_factory=list)`) so the reconciler/renderer can walk both types the same way. The prompt also scopes a **character to a single individual** (one person or one creature): a whole people/race/species/culture taken as a group is NOT a character but the separate `PeopleAndCultures` lore type, so a creature-*kind* (e.g. "direwolves") isn't double-listed under both Characters and People & Cultures — the reconciler dedups only *within* a type, never across them, so this boundary has to live in the prompt. The prompt also captures a **named individual even in a historical/legendary/past-tense context** (a famous long-dead figure like the "Wizard Strong" is still a character), kept strictly scoped to individuals so families/houses/clans/dynasties and whole peoples never leak in as characters. **Scope guards, all parked for later:** no `input()`/interactive confirmation (the player→character review step lives in the orchestrator *after* the Phase 4.1 reconciler), the collision flag is a **log line only** (no `needs_review` field on the model), no entity/alias merging (reconciler 4.1), no `is_pc`/`player_name` consistency cross-check, no DM-specific handling. `history_extractor.py` (done, Phase 3.5) is `HistoryExtractor(BaseExtractor)`, the **third and final** extractor: `extract(messages) -> list[HistoryEvent]` (inherited), with no `__init__` (it injects nothing — unlike Characters), just a class-attr `system_prompt` and a `_build_entry`. It is **structurally different** from the other two: a `HistoryEvent` has **no `details` list** — it's one prose `description` backed by a **flat** `supporting_quotes` list — so `_build_entry` does NOT copy the Location/Character detail loop; it loops a flat `quotes` list (each entry just `quote` + `source_id`, no per-detail text, because the description IS the single summary). **Order matters** in `_build_entry`: `description` is validated **first** (the *only* drop-the-event case — an event with no description is a label pointing at nothing) because the `name` fallback derives from it; a missing/blank `name` does NOT drop the event but falls back to a trimmed first-sentence of the description (`description.strip().split(".")[0][:80]`), since the description is real lore and losing it over a missing *label* would be silly. **`scope` coercion** is the other new piece: because `HistoryEvent.scope` is now the strict `Scope` Enum (which *rejects* off-menu values and would make the `except ValidationError` drop the whole event), the extractor **coerces the raw scope before the model sees it** — `.strip().lower()` (so `"World"`/`" world "` pass without defaulting), and anything not in `VALID_SCOPES` (derived `{s.value for s in Scope}`, so the list can't drift) defaults to **`"world"` and logs** — `"world"` not the narrowest bucket on purpose, because a misfiled event only gets re-filed if it's *visible* in the loud front-of-wiki bucket rather than hidden in `personal`. The coercion stays **minimal** (three values + default, no fuzzy synonym mapping). **Empty-quotes is kept-but-flagged, not dropped:** if every quote fails the verbatim check, the event is still emitted (missing lore is the worse sin) but logged loudly — more sensitive than the other two because a Location's *name* is a real chat mention while a history event's name is **model-generated**, so a zero-quote event has nothing anchoring it to the log. **`chronological_position` is deliberately never set by the extractor** (and never asked of Claude — ordering info is preserved *inside the `description` sentence* instead): assigning a real global ordering needs a pass that sees every event at once, so the field stays on the model as a **mailbox** the later timeline pass fills and the renderer (4.4) reads. **`date_text` (`Optional[str] = None`, done):** the in-world date **exactly as the campaign stated it** ("342 AR", "the Third Age"), or `None` when none is stated — promoted out of the description prose into a first-class field so the renderer can show a clean date prefix and the **4.1b timeline pass** can find it reliably no matter how the sentence was phrased. The extractor **captures it verbatim** (step 4b: `.strip()` only — no parsing, normalizing, or number-conversion; a non-string/blank value defaults to `None`), and a **relative clue** ("before the Empire fell") is **not** a date — it stays in the description with `date_text` null. Crucially it is **not** `chronological_position` (the prompt still forbids any position number); capturing a stated date and *ordering* events stay separate jobs. Backward-compatible: a dateless campaign (like the original logs) gets `date_text=None` throughout and the pipeline is unchanged. **`calendar_system` (`Optional[str] = None`, Fork B):** which calendar system an event's date is in ("AR years", "Elder Scrolls eras"). Like `chronological_position` (and *unlike* `date_text`), the **extractor never sets it** — the **4.1b timeline pass derives it**, because assigning a *consistent* system label across events (and recognizing that two different notations like "1347" / "Third Era 347" are the same system) needs the whole-timeline view a per-batch extractor can't have. It enables **Fork B**: the renderer (4.4) groups events into one ordered timeline **per calendar system**, so a campaign running multiple dating systems gets a faithful separate timeline for each. The 4.1a reconciler leaves it `None` at merge time (a 4.1b field, so `_combine_group`'s History branch passes `calendar_system=None` for symmetry next to `chronological_position=None`); a single-system/dateless campaign gets `None` throughout — fully backward-compatible. **Scope guards (parked):** no timeline/position building, no entity merging or ordering even within a batch, minimal scope coercion. `organization_extractor.py` (done) is `OrganizationExtractor(BaseExtractor)`, the first of the three **typed-lore** extractors that replace the retired `OtherDetail` catch-all: `extract(messages) -> list[Organization]` (inherited), no `__init__`, just a class-attr `system_prompt` + a `_build_entry`. Its **inclusion gate is wider than "has a proper name":** an organization qualifies if it's named OR if it's unnamed but clearly **tied** to a specific location/character/event ("the council that rules Gol"), in which case Claude synthesizes a short descriptive label as the `name`. A **proper name alone is sufficient even with no other detail stated** — a name-only org is captured (carrying the name itself as its single supporting quote), and a bare comma-separated list of named groups (e.g. sports teams) yields one org per name; only a vague group with **neither** a name **nor** a tie ("some merchants") is dropped. The **Location↔Organization split** is the load-bearing boundary: a realm like the Krieger Imperium is a PLACE in the locations extractor (territory/geography) and the governing BODY here (who rules it, how it's structured) — the same realm legitimately appears in **both**, and this extractor captures only the group/governance side (a lone individual is a Character; a whole people/culture is the future PeopleAndCultures extractor). Its `_build_entry` mirrors `LocationsExtractor`'s detail loop but processes **details before the name**, because a missing name falls back to a short form (`[:80]`) of the first surviving detail (the **History-style keep-don't-drop** move) — and it drops the entity only when it has *neither* a usable name *nor* any surviving detail. `item_extractor.py` (done) is `ItemExtractor(BaseExtractor)`, the second typed-lore extractor: `extract(messages) -> list[Item]` (inherited), no `__init__`, the **same shape as `OrganizationExtractor`** — the wider named-OR-tied inclusion gate (with a synthesized short label for a tied-but-unnamed object) and the details-before-name `[:80]` fallback in `_build_entry`. Its bar: an **item** is a physical object you could in principle pick up or carry (a named or tied weapon, armor, artifact, relic, or treasure); ordinary loot merely being bought/sold/counted ("a regular dagger and some rope") is skipped, and a place/person/organization/people is some other extractor's job. `people_and_cultures_extractor.py` (done) is `PeopleAndCulturesExtractor(BaseExtractor)`, the third typed-lore extractor: `extract(messages) -> list[PeopleAndCultures]` (inherited), no `__init__`, the same `_build_entry` shape (details-before-name `[:80]` fallback). It captures a **collective group defined by shared identity** — a race, species, ethnic group, tribe/clan, a nation's people, or a culture ("the Krieg", "direwolves" as a kind). Unlike Organizations/Items it has **no inclusion gate**: any named or clearly-described distinct group counts (no proper name or tie required; a short label is synthesized if unnamed). Two easy-to-confuse boundaries keep it distinct: a single **individual** is a Character ("Kriggy"; one named direwolf in a fight), and a formal, structured **body** is an Organization ("the Krieger Imperium", their state) — the people themselves ("the Krieg") belong here. (This pairs with a one-line clarification to the **characters** prompt so a creature-kind isn't double-counted as a character; both must be in place before a real end-to-end run.) With Locations/Characters/History plus the three typed categories (Organizations/Items/People & Cultures) all done, the extractor layer is complete; the next consumer of all extractor output is the Phase 4.1 reconciler, which merges duplicate entities and unifies aliases across the whole run. `reconciler.py` (done, Phase 4.1a) is `Reconciler(BaseAgent)` — it inherits `BaseAgent` **directly**, like the noise filter and **not** `BaseExtractor`, because it shares none of the extractor spine: it **does NOT batch** (de-dup is global *within* a type — a duplicate split across two batches is invisible, so the whole one-type list goes in a **single** call; fine at our scale of tens-of-entries-per-type) and it **introduces no new quotes** (nothing to verbatim-verify — quotes ride along **by reference** in pure Python). It uses **Sonnet** (the extractors' model/config — precision merge/contradiction reasoning, not a Haiku classification job). The public method `reconcile(entries) -> list` takes one entity type and returns that same type; the orchestrator (later phase) calls it **once per type**, and it de-dups **within a type only** — cross-type separation (keeping "Direwolves" out of both Characters *and* People & Cultures) is already the extractor prompts' job. **The load-bearing split is LLM-decides / Python-assembles:** the LLM only emits a `ReconcileDecision` (which entries merge, the `canonical` name, which details conflict, which pairs are suspicious) and a **pure-Python combiner** (`_combine_group`) does the actual fact-merging straight from the *original* objects — unioning aliases (every losing `name` becomes an alias; canonical never aliases itself), concatenating `details` with **exact-dupe-only** removal (`_dedup_preserve_order`, a light `.strip()` key so a subtly-different fact is never eaten), and deduping `Quote`s on the full **(text, speaker, source_file)** triple (two different speakers attesting the same fact both survive — that's *more* evidence). Because Python physically can't paraphrase a string it's appending to a list, **rewriting a fact is impossible by construction**, the same reason as the extractors' LLM-reasons / `_build_entry`-assembles shape, one layer up. `len(entries) < 2` short-circuits with **no API call**. **Conservative posture:** a false merge fabricates a Frankenstein entity (the sin avoided); a false split is just a harmless duplicate page caught on review — so merge **only on strong evidence** (a stated alias, or one name already in another's `aliases`), and murky pairs go to `possible_duplicates` (a findable `[REVIEW]` log line, **not** merged). **Typo handling:** spelling-closeness is a *trigger to investigate*, never a decider — one edit separates **both** "Maltaav"/"Maltraav" (a real typo → merge) **and** "CJ"/"DJ" (siblings → don't), so context decides; a **short-name rule** (names ≤ `SHORT_NAME_LEN`=3 chars, e.g. initials) is **stated-alias-only**, enforced both in the prompt and by a pure-Python `_short_name_veto` (it fires only when a short name is in play, and errs toward veto since over-blocking just yields a duplicate page). **Scalar resolution (pure Python, after the LLM parse):** `is_pc` → True wins (False = absence of evidence; quiet `debug` log); `scope` → broadest wins via `_resolve_scope` (matches History's default-to-`world` philosophy — a too-broad event is loud and gets corrected, a too-narrow one hides; quiet `debug` log); `date_text` (HistoryEvent only) → a stated date beats `None` via `_resolve_date_text`, and on a **clash** (two merged events stating *different* dates) it keeps the first and logs quietly at `debug` — non-destructive, since the other date still survives verbatim in the merged event's quotes/description — so merging duplicate events never silently drops a stated date; `player_name` → a name beats `None`, but two **different** real names **veto** the merge (`_VetoMerge`, caught by the apply loop → entries kept separate + a loud `[REVIEW]` flag) rather than fabricating a winner, because two humans behind one character usually means the merge itself is wrong (a rare player-handoff is the reason it's a veto, not a hard block); `chronological_position` stays **untouched (`None`)** at 4.1a — the 4.1b timeline pass fills it. **Contradiction handling:** a genuine semantic disagreement between two merged details (`DetailConflict`) becomes a **rich, findable `[REVIEW]` log line** (entity name, both detail texts, both sources, the LLM's note) that Phase 5.3 funnels into `review.txt`; **both** details are kept and there is **no model field** for it. The `[REVIEW]` prefix marks every loud human-actionable flag; the quiet auto-resolved `is_pc`/`scope` clashes deliberately log at `debug` and stay out of the review queue. **Error handling:** the `ReconcileDecision` is Pydantic-validated *and* run through a `_validate_decision` sanity pass (every index in range; no index reused across two groups; **every merge group has ≥2 members** — an empty/one-entry "merge" is malformed and would otherwise crash the combiner's `members[0]`, so it's rejected here and re-guarded by a skip in `_apply`; each `canonical` is genuinely a name/alias of one of its members — so even the heading can't be invented) — any problem is treated like bad JSON and **retried up to 3×**; total failure returns the entries **unmerged** with a loud `error` (under-merge is the safe direction). Parsing is tolerant on purpose: `_parse_decision` tries the fence-stripped text first, then falls back to `_extract_json_object` (a brace-balanced, string-aware scan) so a Sonnet reply wrapped in a conversational preamble — which `strip_code_fences` can't peel — still yields the embedded object instead of burning all three retries on a parse error. And because the validator matches `canonical` case-/whitespace-insensitively, the combiner **snaps it back to the verbatim member name/alias** (`_resolve_canonical`, preferring a name over an alias) before using it as the heading — otherwise a recased "lake mundi" would become the page title and demote the real "Lake Mundi" into the aliases. **The "cross-reference index" originally floated for 4.1a was dropped** — nothing downstream consumes it (the 4.3 cross-link pass builds its own slug map and blind-scans the text; no renderer reads a backlinks structure); if a "See also" feature ever lands it'll be added later as pure Python. **Phase 4.1b (the timeline-ordering pass) is complete** — built in two parts (the pure-Python *engine* and the *LLM layer*), both living in `reconciler.py`; `Reconciler.order_history(events)` is the entry point the Phase 4.5 orchestrator calls on the deduplicated `HistoryEvent`s after `reconcile()`. It runs **after** the 4.1a merge, over the deduplicated `HistoryEvent`s, and fills their two timeline fields (`calendar_system` + `chronological_position`). **Model:** a sorted **spine of dated events** with **gaps** between them, into which relative (undated) events get woven. A date is a **tuple of parts, biggest unit first** (`[1347]` for "1347", `[4, 200]` for "4th Era 200"), so `_build_spine_and_gaps` tuple-sorts element-by-element with **no calendar arithmetic** — and **Python owns every `chronological_position`; the LLM never emits one** (the contracts `DateDecision`/`DatedEvent` + `PlacementDecision`/`GapPlacement` in `models/reconcile.py` carry only indices, system labels, sortable `parts`, and gap IDs). Same-date events **collapse into one rank-group** (a tie → no phantom gap, and "after Founding"/"after Charter" point at the *same* gap; tied markers still get adjacent positions). **The `(undated)` pseudo-system** (`UNDATED` constant) is always present — a single gap for relatively-ordered date-less events, which get `calendar_system=None`; a fully-dateless campaign is just the case where it's the *only* system (**same code path**, zero markers → one gap). That gives the renderer (4.4) a clean **three-way read**: `calendar_system`+position set → a dated timeline; `None`+position set → the undated-but-ordered timeline; `None`+position `None` → **Could Not Place**. **Gap IDs** (`"AR years#1"`, via `_gap_id`) are **opaque keys** matched by exact string against a lookup dict, never parsed back apart — so a label with a `#`/space can't break them, and a stray/hallucinated gap ref just falls to Could Not Place. `_weave_and_stamp` walks each system's spine, drops placed relatives into their gaps in order, stamps `chronological_position = 0,1,2,…` **per system** (each timeline numbers from zero; the renderer sorts within each separately), and returns **new events via `model_copy` — never mutating the inputs**. **Two guard layers:** `_sanity_guard_parts` is best-effort — it rejects a `parts` tuple sharing **no digit** with a date that *has* digits (catching `[343]` for "342 AR"), but **trusts a word-only date** ("the Third Age") since pure Python can't parse calendar notation, with the verbatim `date_text` as the human safety net and a slip being at worst a minor mis-sort, never lost/fabricated lore; and the structural validators `_validate_date_decision` / `_validate_placement_decision` (index range, duplicate index/gap, an event with no `date_text`, non-positive/empty `parts`, an empty system label, an unknown gap, double-placement, or a *dated* event the LLM tried to re-place by gap) which **Brief B retries on**, like 4.1a. The split is deliberate: a *guard* failure drops a single event to relative placement without failing the call; a *validation* failure retries the whole call. **The LLM layer (`order_history`)** wires **two `call_claude` calls** onto that engine: Call 1 (`DATE_EXTRACTION_PROMPT`) reads each dated event into a `system` label + sortable `parts` tuple → a `DateDecision`; Python sorts it (`_build_spine_and_gaps`); Call 2 (`PLACEMENT_PROMPT`) drops the undated events into gaps by ID → a `PlacementDecision`; Python weaves + stamps. **The LLM emits sort keys and gap choices, never positions.** **Call 1 is skipped entirely** when no event has a `date_text` (a fully-dateless campaign makes a single placement call), and **Call 2 is skipped** when nothing is undated. **Graceful degradation, because `_weave_and_stamp` always runs:** a failed Call 1 → empty spine → events ordered relatively or Could Not Place; a failed Call 2 → the dated spine still stamps, only relatives → Could Not Place; a `_sanity_guard_parts` failure on one event drops *just that event* to relative placement (loud `[REVIEW]` log). A total LLM failure yields a *less-ordered*, never *corrupted*, timeline. **Same plumbing as 4.1a**, now run twice: the tolerant fence/preamble JSON parse (`_parse_json_model`, generalizing `_parse_decision` to any model) and the parse → validate → retry-3× → safe-fallback loop, exercised by the `FakeClient` harness. The **system labels are the LLM's job too** — it uses a *consistent label per calendar* and merges interchangeable notations ("1347" / "Third Era 347") into one system **only when the text states the equivalence**, never via real-world calendar knowledge.
- `renderer/` — pure-Python markdown generation (no LLM). `footnotes.py` (`FootnoteRegistry`, done, Phase 4.2) mints stable, deduplicated `[^N]` footnote numbers from `Quote` objects (dedup key = the `(text, speaker, source_file)` triple the reconciler dedups on, except the registry additionally whitespace-collapses the text via a shared `_normalize_quote_text` so internal newlines/tabs or stray edge spaces can't split one footnote — same field shape, stricter text match, not a byte-identical key) and renders the `## Footnotes` definitions block. It is **pure, no-I/O, no-log** — every input is an already-validated pydantic `Quote`, so there's nothing to police: `add(quote) -> int` is idempotent per distinct quote (an explicit `_next` counter, never `len()+1`, so a dedup-hit early-return can't reissue a number), and `render_definitions() -> str` returns the heading + `[^N]:` lines (each quote flattened to one line and wrapped in a **code span** so roleplay asterisks/underscores render literally) or `""` when empty (one emptiness check gates heading+body so 4.4 never peeks inside). Numbering is **render-order**, so rendering must stay single-threaded. The `[^N]` *insertion into prose* and document placement are 4.4's job; more renderer modules arrive in 4.4. `crosslink.py` (`slugify` / `build_crosslink_map` / `add_crosslinks`, done, Phase 4.3) is the **cross-link pass** — pure-Python, no-LLM, no-network (footnotes.py's sibling in the deterministic outer layer; all the expensive LLM work is cached upstream) — turning a bare entity name in already-rendered body prose ("Lake Mundi") into an internal link (`[Lake Mundi](#lake-mundi)`). Built and tested in **isolation**: the real renderer is Phase 4.4 and doesn't exist yet, so this runs on **fabricated** markdown fixtures and 4.4 will `import` it later (it does NOT create/touch `renderer/markdown.py`). **Anti-hallucination ethos:** a wrong link is a quiet lie, so the bias is to **miss a legit link before ever manufacturing a wrong one** — matching is **exact** (modulo NFC + case + self-defined boundaries + the article rule) with **no** fuzzy/edit-distance/typo-tolerant matching anywhere (the prose scanned is the model's clean output; typos survive only in verbatim quotes, quarantined in the footnotes block). **`slugify(name)`** is the single source of truth for anchor ids — we **own our anchors** (4.4 stamps `<a id>` from the same table the linker reads, so they can't drift): NFKD ASCII-fold (drop combining marks, keep ASCII — "Théoden"→"theoden"), lowercase, spaces→hyphens, **keep internal hyphens** ("Half-Elf"→"half-elf") but **strip apostrophes** ("Mal'taav"→"maltaav"), collapse+trim; an all-punctuation name slugs to `""` and the **empty-slug fallback** (`entity-<N>` by stable index + `[REVIEW]`) lives in the **map**, not slugify (only the map has the index). NFKD already folds byte-variants, so slugify needs **no** NFC step — **NFC is applied only at the matching layer** (build-time surface forms + match-time prose), the one place two byte-identical strings must compare equal. **`build_crosslink_map(noun_entities, events=None, common_words=None)`** builds the **single source of truth once** over the **five noun types** (`Location`/`Character`/`Organization`/`Item`/`PeopleAndCultures` — each a link **target** *and* a **source** via its `name`+`aliases`) **plus the history events (4.4)**: an **eligible** event — its article-stripped name isn't sentence-ish, judged by the **same `_looks_sentence_ish` gate** the entity source pool uses — is **both target and source** (it gets an anchor; its `name`+`aliases` join the pool), while a **sentence-shaped/gated-out** event (the extractor fallback-name case) stays **neither** (no anchor, not in the pool) — its `description` is still run through the walk at render time so noun mentions inside it light up. The asymmetry is deliberate — **entities always get an anchor** regardless of the gate; **events must clear the gate to earn one** — and events are anchored **after** the entities against the shared `used_anchors` set, so an event-vs-entity slug clash leaves the entity the clean slug (`riverton`) and suffixes the event (`riverton-2`): the "entities before events" tiebreak, which falls out of pass order with no explicit type-ranking, and from there an anchored event is **just another claimant** — Passes 3–4 resolve event-vs-entity and event-vs-event clashes uniformly, unchanged. The returned `CrosslinkMap` (a frozen dataclass) exposes `anchors` (name→final anchor, **entity-only** — events never enter it), a parallel `entity_anchors` (authoritative per-entity — correct even when two entities share a name), **`event_anchors`** (parallel to the events passed in: the event's anchor, or `None` where it was gated out — the renderer stamps nothing there; an empty-slug event falls back to `event-<N>`, which can't collide with an `entity-<N>` fallback), the longest-first `sources` pool of `(surface, anchor)` pairs, the compiled `pattern`, and a private `_lookup` (surface→`(anchor, article_required)`). **Every messy case is resolved here, once, never during the walk:** slug collisions (two different entities slugging the same → suffix `riverton`, `riverton-2`, … + `[REVIEW]`; a realm that's both a Location and an Organization thus gets two suffixed anchors and its shared surface drops out as ambiguous); alias-collides-with-a-real-name (real name wins, alias dropped + `[REVIEW]`); same alias on two entities (can't pick → out of pool + `[REVIEW]`); a **source-eligibility gate** that holds **sentence-ish** surfaces (>6 words, or internal `.!?;:`) out of the **source** pool — they keep their anchor as a **target** — to defang extractor fallback names by design; and a **common-word gate** from `config/crosslink_words.json` (`{"require_article": [], "never_link": []}`, **both default empty** so a fresh clone runs clean) where `require_article` words fire only with a leading "the" and `never_link` words are held fully out, both matched against the **article-stripped** surface form (so the config lists bare words). Names and aliases share **one** pool sorted longest-first **together** (an alias can outrun another entity's whole name — "The Brotherhood of the Phoenix Blood" vs. a bare "Krieger"). A separate tolerant `load_crosslink_words` (missing file → both empty) is the orchestrator's to call and thread in, like the speaker map — `build_crosslink_map` itself does **no** file I/O. **`add_crosslinks(block, crosslink_map, this_anchor)`** runs the weave over **one** block (an entity page, or a single event description). A **no-go pre-pass** tapes off ATX headings, fenced code blocks, inline code spans, and existing `[text](url)` links (footnote `[^N]` markers are inert and need no handling); the block is **NFC'd once up front** so no-go detection and matching share stable indices. Matching is **one left-to-right pass of a single longest-first regex via `re.finditer`** — non-overlapping, which makes **re-linking your own output structurally impossible** (no manual cursor, no sequential `str.replace`). Matches are **case-sensitive**, use **self-defined word boundaries** (apostrophe/hyphen are word-internal, so bare "Mal" never fires inside "Mal'taav" and "Riverton" never inside "Rivertown"/"preRiverton" — a plain `\b` would mis-split), and the **article rule** (a leading "the"/"The" is **never** part of the link — always emitted outside the brackets with its original casing; only whether it's *required* to fire changes by surface type — a proper noun fires with or without, a `require_article` common word only with "the"). **First-occurrence + self-suppression are one rule:** a per-block `seen` set of **anchor ids**, pre-seeded with `this_anchor`, so a second mention of an entity stays plain *and* the page never links to itself (keyed on the **target anchor**, so an alias resolving to the page's own anchor is suppressed too); `seen` resets per block. Tests are `tests/test_crosslink.py` (fabricated fixtures, every brief case + additive hardening for NFC byte-variant *matching*, the left word boundary, and lowercase-only prose isolated from the `seen` rule — the last two added after an adversarial review found the originals could pass a wrong-link regression). **Deferred to the rest of 4.4:** *stamping* the event anchors into rendered output as navigable timeline anchors (the pool-promotion + anchor-minting half of the old `[DESIGN]` item landed with the `events` param above; the navigable half needs 4.4's timeline rendering), a "see also"/backlinks structure, and Wikipedia-style bolding of suppressed self-mentions.
- `main.py` (top-level) — pipeline entry point. Right now its one real job is to call `load_dotenv()` so the Anthropic SDK can read `ANTHROPIC_API_KEY` from the environment (a `.env` file is NOT auto-loaded, and key-loading belongs here, not in `base.py`). The parse → filter → agents → wiki wiring fills in over later phases.

## Chat log format
Each message ends with a **footer** line — either `+16303463392 MM/DD/YYYY HH:MM:SS` (phone-prefixed sender) or a bare `MM/DD/YYYY HH:MM:SS` (the exporter) — and the phone names the message *above* it (footer, not header). The parser maps the phone through the speaker map; no phone → exporter; an unknown phone falls back to the raw number + a logged warning. The 1-on-1 log has no phone numbers at all, so there the sender is read from body left/right alignment instead. Real exports are truncated mid-message (final footer cut off); the parser recovers that last message rather than dropping it. Full quirk catalogue in `FORMAT_NOTES.md`.

## Testing conventions
Use pytest's `tmp_path` fixture to write throwaway config/log files rather than touching real ones. Test that bad input raises the right error with `pytest.raises(...)`.

Live/API tests (Phase 3.10: the six extractors against real Claude) are marked `@pytest.mark.integration`, **deselected by default** (`pytest.ini` sets `addopts = -m "not integration"`, so plain `pytest` never spends credits) and opted into with `pytest -m integration`. They `skipif` themselves when `ANTHROPIC_API_KEY` is absent — and the repo-root `conftest.py` calls `load_dotenv()` so a key in `.env` is loaded *before* that skip check runs (no false skip). Their assertions are deliberately loose (name/alias substring membership, counts, scope, emptiness — not exact strings) because LLM output isn't deterministic; the fact-vs-quote faithfulness check is manual, via the per-extractor eyeball reports each run writes to `tests/output/`. Fixture messages split by privacy: a **committed** synthetic module (`tests/fixtures/synthetic_messages.py`, fabricated boundary cases, runnable by anyone with a key) and a **gitignored** real-chat module (`tests/fixtures/real_messages.py`, the group's private campaign — same principle as `logs/`); the live suite imports the real cases in a `try/except ImportError` so a fresh clone runs just the synthetic subset. `tests/output/` is gitignored too. The shared `Case` dataclass + `Message` builder live in the committed `tests/fixtures/case.py`.
